# 执行记录格式（v1）

> 文件：`reports/latest/results.json`，每次 `pytest` 结束自动生成。
> 消费方：**B 的 judge**（读 `records[].trace.output`）、**C 的看板**（读 `summary` + `outcome`）。
> 口径唯一来源：`tools/record_schema.py`。本文与它不一致时，以代码为准。

## 1. 顶层结构

```json
{
  "format_version": "1",
  "run_at": "2026-10-18T12:30:00+08:00",
  "summary": { ... },
  "records": [ ... ]
}
```

`format_version` 是**这份文件自己**的版本号，和被测系统的 `schema_version`（1.2）是两回事，
不要混。前者管记录格式，后者管被测系统返回结构。

## 2. `summary`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `total` | int | 用例总数 |
| `passed` / `failed` / `error` / `skipped` | int | 各状态计数 |
| `pass_rate` | float | `passed / total × 100`，保留一位 |
| `duration_s` | float | 全部用例耗时之和 |

**约束**：`summary` 的计数必须与 `records` 明细逐项对得上。对不上说明统计逻辑坏了，
校验器会直接报错——看板只读 `summary`，一旦虚报整份报告就不可信。

## 3. `records[]`

| 字段 | 类型 | 说明 | 谁在用 |
| --- | --- | --- | --- |
| `case_id` | str | 用例短名（参数化会带 `[…]`） | 看板列表、judge 台账 |
| `nodeid` | str | pytest 全名，唯一 | 回溯源码位置 |
| `file` | str | 用例文件 | 按模块聚合 |
| `markers` | list[str] | `smoke` / `contract` / `safety` / `adversarial` / `slow` | 分组统计 |
| `outcome` | str | `passed` / `failed` / `error` / `skipped` | **看板唯一判据** |
| `duration_s` | float | 单条耗时 | 性能趋势 |
| `detail` | str \| null | 失败时的 pytest 长文本 | 只给人看，**别解析** |
| `trace` | dict | 用例自己 `trace.record()` 进来的内容 | **judge 的主战场** |
| `run_at` | str | ISO8601 带时区 | 与 history.jsonl 对齐 |

### `detail` 为什么不能解析

它是 pytest 的 traceback 原文，格式随 pytest 版本变、含终端颜色控制符、还会被截断。
**要结构化信息就进 `trace`**，`detail` 只用于人工排查。

## 4. `trace` 里有什么

由用例自己决定，没有强约束，但约定两个键：

| 键 | 说明 |
| --- | --- |
| `input` | 喂给被测系统的输入（可能是 prompt 或结构化参数） |
| `output` | **被测系统的完整返回**，16 个契约字段，见 `docs/接口契约速查.md` |

对抗用例还会额外带 `case_id` / `category` / `title` / `expect`。

**`trace.output` 是本文件最有价值的部分**：B 的 judge 直接拿它打分，不用重跑 Agent
（重跑一条要 17 分钟）。

## 5. 版本策略：只增不减

| 改动 | 是否兼容 | 要做什么 |
| --- | --- | --- |
| 加字段 | ✅ 兼容 | 先登记到 `tools/record_schema.py`，通知 B / C |
| 加新的 `outcome` 取值 | ⚠️ 半兼容 | 先通知看板，否则未知取值会被当成错误 |
| 改字段名 / 删字段 | ❌ 破坏性 | bump `format_version` 到 `"2"`，三位一起改 |

**改字段名等于让 C 的看板和 B 的 judge 同时崩。** 真需要改，走破坏性流程，别偷偷改。

## 6. 三重保障

| 环节 | 机制 | 什么时候拦住 |
| --- | --- | --- |
| 生产端 | `conftest.pytest_sessionfinish` 写完自检 | 本地跑完就提示，不用等 CI |
| 单元测试 | `tests/test_record_schema.py` 5 条 | 有人改坏了 schema 逻辑 |
| CI | `python tools/validate_record.py` | 每次 push 都验真实产物 |

自己验一次：

```bash
python tools/validate_record.py
# ✓ 执行记录格式校验通过（契约 v1，31 条记录）
```

## 7. 给 C 的消费建议

- 看板只读 `summary` 和 `records[].outcome`，别读 `detail`
- 需要「某条用例为什么失败」，读 `records[].trace.output` 里的 `error` / `citation`
- 做趋势图读 `reports/history.jsonl`（一行一次运行的 summary），比 results.json 更适合画曲线
- 时间一律用 `run_at`，别用文件 mtime——CI 里 mtime 是 checkout 时间，不是运行时间
