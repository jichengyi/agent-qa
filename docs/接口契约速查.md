# 接口契约速查（v1.2）

> 来源：C 提供的《评测接口说明》。本页只做速查，冲突时以原文档为准。
> 用例的断言全部按本页写；字段改名 = 用例全红，所以改字段必须先通知测试侧。

## 1. 入口

```python
from src.api import run

result = run("检索增强生成中的引用幻觉检测方法")
```

**是可直接 import 的函数，不是 HTTP 服务。** HTTP 版（`:8600`，`POST /chat`）是可选项，
返回体与 `run()` 同构，只做「解析请求体 → 调 run → 序列化」。

可选参数：`stage_budget_s`、`timeout_s`、`use_cache`、`evaluate`、`use_retrieval`、
`policy`、`raise_on_error`。既可平铺，也可放进 `options`。

## 2. 返回的 16 个顶层字段

| 字段 | 类型 | 含义 | 测试怎么用 |
| --- | --- | --- | --- |
| `schema_version` | str | 当前 `1.2` | 结构兼容性判断 |
| `engine` | str | 固定 `research-assistant` | 横向评测区分 |
| `run_id` | str | `eval-YYYYMMDD-HHMMSS-xx` | 关联日志与 trace |
| `ok` | bool | 流程是否跑完 | **通过率分母** |
| `prompt` | str | 回显输入（已 strip） | 输入输出对齐 |
| `answer` | str | 报告全文 | 质量打分 |
| `tool_calls` | list | 按真实顺序排列 | 工具使用正确性 |
| `tools` | list | 去重保序的工具名 | 覆盖率统计 |
| `references` | list | 本次检索到的来源 | 引用溯源、命中率 |
| `citation` | dict | 引用质量指标 | **幻觉检测** |
| `self_eval` | dict/null | `evaluate=True` 时的内置自评 | 与外部打分交叉验证 |
| `stages` | list | 五阶段耗时与状态 | 性能分析 |
| `retrieval_notes` | list | 逐源失败原因 | 解释「为什么没来源」 |
| `usage` | dict | 耗时/工具数/来源数/**context 截断**/**safety 声明** | 成本核算、判定工具是否该调用 |
| `warnings` | list | 降级但仍成功 | 这份结果要不要信 |
| `error` | dict/null | `{type, message, where}` | 失败归因 |

## 3. `tool_calls[]` 语义

```json
{"seq": 1, "name": "search_papers_web", "args": {...},
 "status": "ok", "duration_ms": 1832.4, "result": {"records": 6}}
```

四条约定：

1. `seq` 从 **1 连续递增**，是真实执行顺序，不是按名字排序。
2. **失败也留记录**：`status="error"` + `error` 字段。工具失败 ≠ 工具没被调用。
3. 参数不脱敏但截断（字符串 2000 字、列表 20 项）。
4. `result` 是摘要不是原始返回。

算「工具」的只有三个：`search_papers_web`、`retrieve_local_library`、`search_local_knowledge`。
**LLM 调用不算工具**，它在 `stages` 里。

## 4. `references[]` 语义

- `id` 与正文 `[n]` **严格一致**：正文 `[1]` 就是 `references` 里 `id=1` 的那条。
- `cited` / `cite_count` 是**正文**统计出来的（先剥离 `## 参考文献` 块再数 `[n]`）。
- `kind`：`web` / `local_library` / `skill` / `experience`。
- 本地文献带 `path`；技能带 `path` + `score`。
- **v1.2 起按文档聚合**：一篇 PDF 命中 5 段只算 **1 条来源**，段数记在 `chunk_count`。
  统计来源数、算 RAG 命中率都必须按 `path` / `doi` 去重后再数——
  `len(references)` 不再等于 chunk 数，也不等于「独立证据数」。

## 5. `citation` 指标

> ⚠️ **真机返回是 10 键，本仓库替身只实现了 6 键**。键数以 C 的《评测接口说明》为准；
> 断言只依赖下面这 6 个必备键，**不要断言键数相等**，否则真机一上来就红。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `markers` | int | 正文引用标记数（去重） |
| `available` | int | 本次真实提供的来源数 |
| `valid` | int | 能对上号的引用数 |
| `fabricated` | **list[int]** | **引用了不存在的编号，是列表不是计数**（无编造时为 `[]`） |
| `faithfulness` | **float \| null** | `valid / markers`，**零引用时为 `null`**（不制造虚假分母） |
| `coverage` | float | 被引用到的来源占比（资料利用率，**不是幻觉率**），零来源时为 `0.0` |

### 两条断言纪律（都是「离线绿、真机红」的坑）

```python
# ① 判「无编造」——fabricated 是列表
assert len(citation["fabricated"]) == 0      # ✅
assert citation["fabricated"] == []          # ✅
assert citation["fabricated"] == 0           # ❌ 真机 [] == 0 是 False

# ② 判「零引用」——不要看 faithfulness
assert citation["markers"] == 0              # ✅ 正确判据
assert citation["faithfulness"] is None      # ✅ 零引用时确实为 null
assert citation["faithfulness"] == 0         # ❌ 真机返回 null，且 null 参与比较会 TypeError
```

> `fabricated` 写成计数（10-19 修正）、`faithfulness` 零引用写成 0（10-19 修正），
> 两处都是「替身能过、真机必红」的分叉，根因相同：**替身按直觉实现了指标，没有对齐真机的空值语义**。

## 6. 失败语义（最重要）

> 除 `raise_on_error=True` 外，**任何情况都不把异常抛给调用方**。

| 场景 | `ok` | 关键字段 |
| --- | --- | --- |
| 空 prompt / 非字符串 | false | `error.type="InvalidPrompt"` |
| 超过 2000 字 | false | `error.type="PromptTooLong"` |
| 超过 `timeout_s` | false | `error.type="TimeoutError"` |
| 超过 `stage_budget_s` | false | `TimeoutError`，带阶段名 |
| **单个检索源失败** | **true** | `tool_calls[i].status="error"` |
| 全部来源失败 | true | `references=[]`，`citation.available=0` |
| 后处理失败 | true | `warnings` 非空，`answer` 照常 |
| 模型调用抛错 | false | `error.type` 为原始异常类 |

HTTP 层另有三个「请求没进门」的状态码，与 `ok` 无关：`400`（非法 JSON / 缺 prompt）、
`413`（>1MB）、`429`（并发超限，按 `Retry-After` 退避）。

**`ok=true` 不代表答得好，只代表流程跑完。** 质量由 `citation` 与外部打分判断。

## 7. 对测试的三条硬约束

1. **先看 `ok` 再断言内容**——`ok=false` 时 `answer` 可能为空，直接断言会误报。
2. **超长输入是「拒绝」不是「截断」**——不要写「截断后仍能答」的用例。
3. **工具失败不改 `ok`**——但要限定注入点：单源可降级（`ok=True`），模型链路挂（`ok=False`）。
   断言名里写清注入点，例如 `test_search_source_503_keeps_ok_true`。

## 8. 缓存与离线（踩过的坑）

### 8.1 批量评测必须 `use_cache=False`

缓存键是 `(prompt, use_retrieval, evaluate, policy, timeout_s, stage_budget_s)`
（`timeout_s` / `stage_budget_s` 是 C 事后补进去的——原来漏了，导致超时用例命中成功缓存）。

三个坑，都实测过：

| 现象 | 后果 |
| --- | --- |
| 缓存键不含**故障注入状态** | 注入不同故障的两条用例，第二条拿到第一条的成功结果 → 假通过 |
| 命中时 `run_id` 不变 | 用 `run_id` 做台账唯一键会把两条记录去重掉；判据应看 `usage.cached` |
| 命中时 `duration_ms` 是上次的旧值 | 任何耗时断言在命中时失效 |

另外：**pytest 路径下用例不会自动清缓存**（被测系统自带的 runner 会清，pytest 不走那段）。
所以本仓库有 `tests/conftest.py`，autouse fixture 进出各清一次。

### 8.2 `MOCK_MODE=1` 不能用来测行为

它把检索整段短路（`research_flow.py:271` 的 `if not settings.MOCK and use_retrieval`），
结果 `tool_calls=[]`、`references=[]`、`citation` 全零。只能验结构，验不了行为。

要测行为用打桩配方 `offline()`：强制 `settings.MOCK=False`，
把联网 / 向量库 / 模型换成确定性假实现，流水线照常跑，几十毫秒跑完、不烧额度。

> **配方文件在 agent-qa 仓库**：`agent_under_test/offline.py`（不是被测系统仓库里的东西）。
> 它依赖被测系统的内部模块（`config.settings` / `src.pipelines.research_flow` / `src.rag.sources`），
> 所以必须先把 `PYTHONPATH` 指向被测系统源码根，否则 import 会失败。
> 在 `research-assistant` 里找不到它是正常的——它属于测试侧。

## 9. `coverage` 不是幻觉率

```
coverage = 被引用到的资料数 / 提供的资料总数      # 资料利用率
```

判幻觉看 `fabricated` / `faithfulness`。跨运行比 `coverage` 必须同时记录
`usage.context.truncated` 与分母——截断时分母本身就是被裁剪后的资料集，不可比。

## 10. `usage.safety`：`tool_calls=[]` ≠ 工具错序

真机冒烟报告（2026-10-18）第 5 节给的判据：

| 标记 | 含义 | 判据 |
| --- | --- | --- |
| `usage.safety.skip_retrieval=true` | 遵从了「别检索」的指令 | 工具为空**合理**，不算缺陷 |
| `usage.safety.no_web=true` | 遵从了「别联网」的指令 | 缺 `search_papers_web` **合理** |
| 两者都是 false 且 `tool_calls=[]` | 该调的工具没调 | **这是缺陷**，但不是「顺序错」 |

**空调用是「缺失」，不是「错序」**——两件事必须分开报，否则缺陷台账会把它们混成一条。

## 11. 真机实测字段口径（2026-10-19 用 `/chat` 逐键核对）

早期这份文档有几处是按假设写的，实测后已经改正。**以本节为准**，下表左列是过去的错误写法。

| 位置 | 过去写的（错） | 真机实测 | 影响 |
| --- | --- | --- | --- |
| 工具数 | `usage.tool_count` | **`usage.tool_calls`**（数字） | 与顶层 `tool_calls`（列表）同名不同型，别混用 |
| 来源数 | `usage.source_count` | **`usage.sources`** | — |
| 上下文上限 | `usage.context.limit` | **`usage.context.budget`** | 断言 `"limit" in ctx` 直接失败 |
| 阶段名 | `stages[].name` | **`stages[].key`** + `label` | 真机是中文 key（调研/综述/方案/报告） |
| WAF 标记 | `usage.context.waf_trimmed` | **不存在** | 已从用例移除 |

完整的嵌套结构（真机 10 键，`usage` 内还有三个子对象）：

```jsonc
"usage": {
  "duration_ms": 7.8,
  "stage_count": 4,
  "tool_calls": 0,          // 数字
  "sources": 0,             // 数字
  "answer_chars": 198,
  "cached": false,
  "cached_at": null,        // 命中缓存时是 "2026-10-19T16:14:11"
  "context": {              // 失败路径下可能是空对象 {}
    "total": 0, "covered": 0, "omitted": [], "chars": 0,
    "budget": 4000, "truncated": false
  },
  "safety": {
    "input_blocked": false, "rule": null,
    "output_blocked": false, "output_rule": null,
    "skip_retrieval": false, "no_web": false
  },
  "evolve": { "issues": [], "absorbed": 0, "queued": false, "generation": 2 }
}
```

`citation` 真机是 **10 键**——除必备的 6 个外还有
`fabrication_rate`（编造占比）/ `has_fabrication`（布尔快捷判据）/
`repaired`（已修复条数）/ `repaired_ids`（修复了哪些编号）。
判「无编造」可以用 `has_fabrication is False`，但**不要断言键数**。

`DEFAULT_TIMEOUT_S` 已从 1200 提到 **1800s**（依据：慢网关日实测 1043s / 1106s）。
评测侧 `timeout_s` 建议 ≥1800；pytest 自己的超时设到 2400，别让它先掐掉用例。

## 12. 失败路径的两个坑（2026-10-19 实测）

限流（`CloudLLMError`）时返回体里：

- `references` 有 10 条，但 `citation.available` 是 **0** —— citation 在生成阶段才算，
  检索阶段的结果没回填。**失败样本的 `coverage` / `faithfulness` 无意义，judge 要跳过。**
- `usage.context` 是 **`{}` 空对象**，不是完整结构。断言 `ctx["budget"]` 会 KeyError，
  先判真值再用。

这两条不是缺陷，是「失败样本不可评分」的边界。B 的 judge 必须识别 `ok=false` 后直接跳过
质量维度，否则会拿一堆 0 分污染均值。
